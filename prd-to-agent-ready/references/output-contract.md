# 需求契约与追踪结构

每次创建或修订工程化 PRD 时读取。采用下列信息契约，按功能规模组织章节；可以合并表格或调整标题，不要求空章节。正文应自包含，后续执行者不需要读取本技能或原始聊天才能理解规则和验收。

## 证据与 ID

使用稳定前缀，例如 `SRC-001`、`REQ-001`、`BR-001`、`SC-001`、`AC-001`、`Q-001`、`CF-001`。沿用已有文档的 ID 体系也可以。新增 ID 唯一，拆分时记录父子关系，删除时保留废弃记录，不重新编号未变更项。

| 记录 | 必需信息 |
| --- | --- |
| Source / SRC | 文件或消息标识、版本或快照信息、具体位置、必要的原文片段、来源类型 |
| Requirement / REQ | 来源与证据性质、输入或事件、前置条件、行为、可观察结果、规则及范围引用、验收引用、关联问题 |
| Business Rule / BR | 来源及需求引用、适用条件、业务判定或约束、结果、例外、数据或配置映射、关联问题 |
| Implementation Scope / SC | 对应需求及规则、需要覆盖的业务能力、涉及的系统边界与依赖、非目标、对应验收及受阻条件 |
| Acceptance Criteria / AC | 对应需求及规则、前置条件、测试输入、执行步骤、可观察预期、校验对象、验证方式、可执行或受阻状态 |
| Question / Q | 缺失信息、必要性、来源或检查依据、影响的 ID、阻塞性及具体范围、处理性质、决策或验证角色、候选选项、当前状态 |
| Conflict / CF | 互相冲突的来源位置及原文、冲突点、影响的需求及验收、关联 Q、解决决定的来源与状态 |

来源定位按材料类型选择：Markdown 标题及段落、带版本的行号、表格页签与单元格、PDF 页码及区域、图片标识及区域。粘贴文本可编号段落并保留必要原文片段。版本未知写 TBD；无可靠行号时不伪造行号。

用户补充决定独立登记为 Source，并保留它取代或澄清的旧来源。代码路径及版本属于实现证据，不能作为策划未决定行为的确认来源。图文矛盾同样进入冲突记录。

证据性质使用以下语义：

- **明示**：原文或已确认补充直接给出的行为。
- **推导**：列出前提 Source、推导过程及适用条件；必须是不需要新业务选择的结论。
- **TBD**：缺少决定或证据，引用 Q；不要填入推测的默认值。
- **冲突**：引用 CF 和 Q；解决前不挑选一方当作规则。

可选建议和技术注意事项不属于以上正式需求证据。单列说明，不能通过生成 ID 将其伪装为原文要求。

## 建议的阅读顺序

1. 目标、范围、非目标、文档版本和整体可执行性。
2. 来源清单、原文覆盖与追踪矩阵。
3. 原子需求、业务规则及实施范围。
4. 适用的状态、时间、数据、配置、UI 与外部交互契约。
5. 观测口径；仅在适用时加入正式实验契约。
6. 验收标准、问题清单及独立冲突清单。
7. 有实际修订时的变更影响；需要时的技术注意事项和非强制建议。

用户指定既有格式时在该格式中保留这些信息，不额外创建重复文档。背景动机未说明时写 TBD，不代填“提升留存”等通用目标。

## 追踪矩阵

矩阵至少表达以下列，支持一对多、多对一关系；详细规则只维护一份，以 ID 引用：

| Source 与原文位置 | Requirement | Business Rule | Implementation Scope | Acceptance Criteria | 证据性质 / 问题 / 可执行性 |
| --- | --- | --- | --- | --- | --- |

维护两个方向的检查：

- **原文 → 需求**：所有重要陈述都有去向。非目标、背景或不明确陈述可指向对应记录，但不能无说明消失。
- **验收 / 规则 → 原文**：每项正式业务预期都能追溯到 Source。需求引用不能掩盖规则本身没有来源。

每条重要需求至少有 AC；每条 BR 引用 Source 和 REQ；每条 SC 引用 REQ 及适用 BR，并关联 AC。没有独立业务判定的纯展示需求可注明 `BR: N/A（仅展示，依据……）`，保持 `SRC → REQ → SC → AC`，不为格式重复制造规则。

从某段原文发现“未定义失败行为”可以登记 Q。它说明检查发现的缺口，不等于原文已经要求某种重试或补偿规则。

## 需求与规则写法

按业务结果拆分，避免把一次用户操作机械拆成技术函数。一次“领取”可能包含不同结果的需求；拆分后仍需交叉引用，保留原文明确的依赖与顺序，未说明的顺序不得补定。

每个需求至少回答：

- 什么状态、用户、数据或事件是输入？
- 哪些前置条件允许该行为？
- 应发生什么行为，完成后有什么可观察结果？
- 哪些条件、异常或边界由 BR 限定？
- 受哪些 Q 或 CF 影响，哪些部分可单独验收？

重要数值同时保留单位、适用范围、比较边界和来源。原文“当天”“完成”“领取成功”等词缺少判定时，引用问题，不擅自换成设备自然日、动画结束或按钮点击。

SC 记录业务能力，例如“领取结果确认、进度恢复、展示刷新所涉及的边界”，不决定必须有哪些类或如何存储。若原文已规定技术约束，保留为带来源的约束；技术建议另列。

## 问题与冲突契约

问题的两组分类分别填写：

| 维度 | 值与含义 |
| --- | --- |
| 阻塞性 | `Blocker`：没有答案无法正确实现所列范围；`Non-blocker`：其余独立范围可推进，仍需说明受影响部分 |
| 处理性质 | `Decision Required`：产品方向或业务取舍；`Technical Validation`：技术可行性或现有能力验证；`Information Gap`：缺少材料或事实 |

一项技术验证也可能是 Blocker。多个性质需要不同责任角色时拆成互相关联的问题，而不是混为一个“待确认”。优先顺序按影响和依赖说明，不默认所有问题同级。

责任人按角色填写，如策划、产品、客户端、服务端、数据分析或 QA；不清楚具体角色则写“角色 TBD”，并说明需要确定决策权。选项只给合理候选，注明未选定。记录原文已给出的期限，不自行生成承诺日期。

冲突表保留双方 Source 和具体差异。只有有权角色的补充决定或明确的版本替代关系才能解决；不能默认代码优先、图片优先或文件时间较新者优先。解决后记录决定来源、受影响 ID 和更新的验收。

## 验收契约

每条 AC 可采用 Given / When / Then，也可采用等价字段，但必须具备：

- **前置条件**：用户资格、初始业务状态、所需配置及外部结果；测试人员应能构造场景。
- **输入与步骤**：具体操作或事件，适用的重复、失败、恢复或边界时序。
- **预期结果**：可观察的业务状态、奖励或收入等副作用、UI 映射以及需要保持不变的对象；不以“正常”“符合预期”代替结果。
- **校验方式**：验证哪些数据、结果或展示；区分自动化可验证与需人工观察的部分，不强制使用某个测试框架。
- **追踪与可执行性**：关联 REQ / BR；缺少预期或前置条件时标为 `BLOCKED（Q-ID）`，明确待补内容。

同一 AC 可覆盖多个需求，但各需求的预期要可分别判断。原文没有定义的异常处理，写受阻验收及 Q，不把“失败后重试三次”等假设作为断言。仅存在 AC ID 不表示已具备可执行覆盖。

验收对象应是目标功能的实际业务行为、数据、配置或展示不变量。核对生成文档是否复述原文属于文档一致性检查，不能替代产品验收，也不计为可执行功能覆盖。

按生命周期检查初始、开启、正常、完成、失败、重复、重进、持久化、断网恢复、时间边界、配置变更、升级、结束和重置。适用项关联 AC 或 Q；不适用项记录范围依据。复杂流程至少覆盖正常、异常、边界三类路径，缺少产品预期时如实标受阻。

验收设计完成不表示实际运行。文档转换不填写虚构的 PASS、测试截图或运行记录；涉及视觉或手感时明确人工验收步骤与预期。

## 变更与交接

修订已有 PRD 时记录变更来源、语义差异和影响集合。沿 `SRC → REQ → BR → SC → AC`，以及状态、配置、指标等交叉引用求影响范围；列出新增、修改、废弃和待重验项。不能只更新正文却保留失效的验收或实验口径。

拆分或合并需求保留历史映射。旧验收结果保留原版本背景，受影响项标记待重验。问题解决后，将答案作为新 Source，更新规则、数据、UI、验收及可执行性，不能只关闭问题而不更新契约。

交付说明至少包含实际产物位置、整体状态、独立可推进范围、阻塞项及其责任角色、已做的文档一致性检查。没有正式需求未决项且契约可执行时才标整体 READY；否则整体 DRAFT，明确局部 READY 的依据。产品签字与实施授权如未提供，不因 READY 标签自动成立。
